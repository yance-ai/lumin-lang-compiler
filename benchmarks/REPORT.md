# Lumyr-Lang 编译器性能基准测试报告

## 1. 测试环境

| 项目 | 配置 |
|------|------|
| CPU | Intel(R) Core(TM) i5-5257U @ 2.70GHz (4 核) |
| 内存 | 8 GB |
| 操作系统 | macOS 12.7.5 (Build 21H1222) |
| C 编译器 | Apple clang 14.0.0 (clang-1400.0.29.202) |
| 优化版 commit | `3ad1eff` (dev 分支 HEAD，含 SSO+栈分配+标量替换) |
| 基线版 commit | `ed15d49` (SSO 之前版本，优化链起点) |
| 测量通道 | 编译通道（`./bin/lumyr -c file.lm -o out && ./out`） |
| 运行次数 | 每个基准每个版本跑 3 次，取中位数 |
| 时间测量 | `/usr/bin/time -l` real time |
| 内存测量 | `/usr/bin/time -l` maximum resident set size |

### 优化链说明

基线 `ed15d49` 之后依次合入的优化：

1. `06e35e4` — 字符串 SSO 内联（<=22 字节免堆分配）
2. `bdfbce7` — 数组栈分配 Phase 1（逃逸分析 + ValueArray 栈分配）
3. `2bfa5e1` — 数组栈分配 Phase 2（items 缓冲区栈分配）
4. `83cf12d` — map 结构体栈分配（ValueMap 栈分配）
5. `9467154` — 标量替换（不逃逸小数组/map 拆解为标量局部变量）
6. `3ad1eff` — 消除标量替换残留栈声明（当前 HEAD）

## 3. GC 对象数对比（gc_delta）

`gc_delta = gc_count(后) - gc_count(前)`，表示基准运行期间 GC 管理的对象净增量。

| 基准测试 | 基线 gc_delta | 优化后 gc_delta | 减少量 | 减少比例 |
|----------|---------------|------------------|--------|----------|
| bench_string | 9,000,000 | 4,000,064 | 4,999,936 | 55.6% |
| bench_array | 4,000,000 | 2,000,000 | 2,000,000 | 50.0% |
| bench_map | 15,500,000 | 3,500,016 | 11,999,984 | 77.4% |
| bench_mixed | 10,500,000 | 0 | 10,500,000 | **100%** |
| bench_gc_pressure | 6,900,000 | 2,700,032 | 4,199,968 | 60.9% |

### 关键发现

- **bench_mixed 实现零 GC 对象**：所有数组和 map 均为只读常量初始化，被标量替换完全消除；短字符串走 SSO 免堆分配。运行期间 `gc_delta = 0`。
- **bench_map GC 对象减少 77.4%**：只读常量 map 被标量替换，仅读写模式的 map 仍需堆分配（含哈希表和字符串键）。
- **bench_string GC 对象减少 55.6%**：短字符串（<=22 字节）走 SSO 免堆，但字符串拼接产生的长字符串仍需堆分配。
- **所有基准的 GC 对象数均显著下降**，即使在执行时间变慢的场景中，内存压力也得到了有效缓解。

## 4. 内存峰值对比（Max RSS）

单位：字节，取三次运行中位数。

| 基准测试 | 基线 Max RSS | 优化后 Max RSS | 减少量 | 减少比例 |
|----------|-------------|----------------|--------|----------|
| bench_string | 400,613,376 | 317,251,584 | 83,361,792 | 20.8% |
| bench_array | 388,124,672 | 293,085,184 | 95,039,488 | 24.5% |
| bench_map | 964,390,912 | 495,886,336 | 468,504,576 | **48.6%** |
| bench_mixed | 594,853,888 | 1,630,208 | 593,223,680 | **99.7%** |
| bench_gc_pressure | 1,974,792,192 | 1,732,608,000 | 242,184,192 | 12.3% |

### 关键发现

- **bench_mixed 内存几乎为零**（1.6 MB vs 595 MB）：标量替换 + SSO 完全消除了堆分配，程序仅需运行时基础内存。
- **bench_map 内存减半**：map 的哈希表和 ValueMap 结构体在只读模式下被完全消除。
- **bench_gc_pressure 内存仍较高**（1.7 GB）：大数组（500 元素）和大 map（20 键）超过栈分配阈值，必须堆分配，GC 来不及回收导致峰值高。

## 5. 总结与分析

### 5.1 收益最大的场景：bench_mixed（4.00x 加速，零 GC）

**原因分析**：
- 所有数组和 map 均为**只读常量初始化**，标量替换将它们完全拆解为 C 局部标量变量，零堆分配。
- 字符串均为短字符串（<=22 字节），SSO 内联免堆分配。
- 整个基准运行期间 `gc_delta = 0`，GC 完全不介入，消除了所有分配/回收开销。
- 内存峰值从 595 MB 降至 1.6 MB（减少 99.7%）。

**这代表了优化链的理论上限**：当代码模式完全匹配优化条件（不逃逸 + 只读 + 常量初始化 + 短字符串）时，可实现数量级的性能提升。

### 5.2 收益显著的场景：bench_map（1.47x 加速）

**原因分析**：
- map 操作本身较重（哈希计算、红黑树/哈希表查找），消除只读 map 的堆分配后收益明显。
- 只读常量 map 被标量替换完全消除（gc_delta 减少 77.4%）。
- 读写模式的 map 仍需堆分配，但占比仅一半。
- 内存峰值减少 48.6%（从 964 MB 降至 496 MB）。

### 5.3 基本持平的场景：bench_array（0.98x）

**原因分析**：
- 数组操作本身非常轻量（下标读写就是指针偏移），即使消除了堆分配，节省的时间有限。
- 只读常量数组被标量替换（gc_delta 减少 50%），但读写模式的数组仍需堆分配。
- 两种模式各占一半，整体时间基本持平。
- 内存仍减少 24.5%，说明栈分配/标量替换在内存层面有效。

### 5.4 反而变慢的场景：bench_string（0.85x，慢 15%）

**原因分析**：
- SSO 字符串在创建和拼接时需要**判断内联/堆模式**，增加了分支开销。
- 字符串拼接 `s1 + ":" + s2` 产生的结果字符串通常超过 22 字节，**仍需堆分配**，SSO 无法覆盖。
- 基线版本的字符串实现更简单（统一堆分配），在纯 CPU 密集的拼接场景中反而更快。
- **但 GC 对象减少 55.6%，内存减少 20.8%**：在长时间运行或内存敏感场景中，SSO 的收益会通过减少 GC 频率和暂停时间体现出来。

### 5.5 反而变慢的场景：bench_gc_pressure（0.85x，慢 17%）

**原因分析**：
- 大数组（500 元素）和大 map（20 键）**超过栈分配阈值**，必须堆分配，优化无法覆盖。
- 优化版本的运行时增加了 SSO/栈分配/标量替换的**基础设施开销**（如逃逸分析标记、SSO 模式判断、栈/堆混合管理），在纯堆分配场景中这些开销成为净负担。
- 优化版本的 GC 可能需要处理更多对象类型（SSO 字符串、栈分配对象的标记），增加了 GC 遍历开销。
- 尽管如此，GC 对象数仍减少 60.9%，内存减少 12.3%。

### 5.6 标量替换的关键限制

通过实验发现，标量替换（完全免堆）有严格的触发条件：

| 条件 | 触发标量替换 | 不触发 |
|------|-------------|--------|
| 初始化值 | 常量字面量 | 变量/表达式 |
| 访问模式 | 只读 | 有写入操作 |
| 逃逸性 | 不逃逸（函数局部） | 逃逸（return/全局/存入其他容器） |
| 数组大小 | <=256 元素 | >256 元素 |

**写入操作是阻止标量替换的最常见原因**。本基准中的 bench_array 和 bench_map 均包含读写模式，因此只有约一半的迭代受益于标量替换。

### 5.7 综合结论

1. **优化链在匹配场景下效果显著**：只读 + 不逃逸 + 常量初始化的小数组/map 和短字符串，可实现 4x 加速和零 GC。
2. **内存层面全面受益**：所有 5 个基准的 GC 对象数和内存峰值均显著下降，即使执行时间变慢的场景也是如此。
3. **CPU 时间收益不均衡**：map 和混合场景收益大，数组持平，字符串和 GC 压力场景因基础设施开销反而变慢。
4. **写入操作限制标量替换**：当前标量替换仅覆盖只读数组/map，实际业务代码中大量读写模式无法受益。
5. **建议后续优化方向**：
   - 扩展标量替换支持写入模式（SSA 形式的数组元素追踪）
   - 优化 SSO 字符串拼接的快速路径（减少模式判断开销）
   - 降低优化基础设施在纯堆分配场景中的开销

## 6. 复现方法

```bash
# 构建优化版（当前 dev 分支）
cd $(cd "$(dirname "$0")/.." && pwd)
./concat_manifest.sh >/dev/null 2>&1 && make all

# 构建基线版（git worktree）
git worktree add /tmp/lumyr-baseline ed15d49
cd /tmp/lumyr-baseline && ./concat_manifest.sh >/dev/null 2>&1 && make all

# 复制基准文件到基线工作目录
mkdir -p /tmp/lumyr-baseline/benchmarks
cp benchmarks/*.lm /tmp/lumyr-baseline/benchmarks/

# 运行完整测量
cd $(cd "$(dirname "$0")/.." && pwd)
bash benchmarks/run_benchmarks.sh
```

单个基准手动运行：
```bash
./bin/lumyr -c benchmarks/bench_mixed.lm -o /tmp/out && /usr/bin/time -l /tmp/out
```
